# BobTV iPhone、iPad 与 Android 手机开发计划

日期：2026-11-20，日本时间。状态：规划草案 v0.2，仅文档，尚未开始应用实现。

## 1. 目标与建议

在现有 Flutter 工程中增加面向个人触控设备的通用播放器体验。按用户最新要求，iPad 与 Android Pad 共用随方向切换的布局：竖屏播放器在上、频道在下，横屏播放器在左、频道在右；iPhone 与 Android 手机以播放为主，通过竖屏底部上拉、横屏右侧左滑的抽屉切换频道，抽屉最多两列、上下滚动，分类针对手指操作重新设计。共用播放、订阅、数据库和资源包解析能力，各设备独立验收。建议先使用一个支持 iPhone/iPad 的 Apple 应用目标和商店条目，无需为两种设备复制整个工程或分别上架。

建议同期纳入 Android 手机适配，复用手机尺寸的布局与数据能力，保留 Android 平板及 TV 的现有交互。Android 手机的正式支持必须经过独立真机验收，不能用平板测试替代。

规划中的 Apple 商店版本首次启动为空；用户自行添加播放列表或兼容资源包地址。频道、分类、节目单、台标可以通过数据同步生成。解析、播放和交互功能随应用提交审核。自定义协议不作为隐藏功能或代码更新通道。

本轮仅做计划和文档。未承诺上架通过，未授权服务器变更、生产发布、应用安装或现有用户数据迁移。

## 3. 产品与架构范围

### 3.1 共享能力

共享订阅模型、频道与线路身份、EPG 绑定、收藏、搜索、播放状态机和错误处理。保留数据提供方的来源归属，多源同名频道不应在导入时无条件合并。用户删除订阅后，不得通过旧维护任务重新创建。

以可用窗口宽高、设备交互类型、输入方式及系统能力决定布局。手机采用播放页与按需呼出的频道抽屉，抽屉最多两列；平板在空间足够时采用播放器在左、频道在右的并排布局。窄窗口的平板可收起频道区为同款抽屉。手机横屏仍保留抽屉。断点先作为设计参数，经过原型验证后确定，不直接把现有 640 逻辑像素断点当作最终方案。

### 3.2 发布渠道与现有用户

采用同源代码和明确的构建渠道配置区分既有发行版与 Apple 空播放器版。商店版构建产物不包含默认频道资源或推荐源入口；启动任务也不得绕过配置再次拉取公共目录。不能仅隐藏界面。

本轮不决定将现有 Android 全量改成空播放器，也不清空桌面或平板用户的数据。Android 手机先复用当前发行渠道，未来是否增加 Google Play 单独规划。

公共目录、诊断、收藏云同步、频道分类、自动线路修复、EPG、台标、远控、投屏、AI 和其他第三方集成逐项形成依赖表。通用播放器的核心导入与播放不应强制依赖 BobTV 账号或固定网关。需要服务器的增强服务作为明确说明的可选能力；首版先不接入尚未梳理清楚的服务。

用户输入的订阅地址、鉴权参数与播放历史默认本地处理；不静默上传给原有诊断、AI、分类或共享线路服务。订阅凭据按系统安全存储能力处理，导出与日志需要脱敏。

### 3.3 首版范围

首版目标：空状态、手动 URL 添加、M3U/M3U8 列表解析、单独流地址播放、订阅管理、频道分组、搜索、收藏、单路播放、全屏、基础 EPG、手动刷新和前台节制同步。注意 M3U8 既可能是频道列表，也可能是单个 HLS 媒体清单，必须区分。

Xtream 复用现有实现，是否进入首版取决于联网与凭据验证结果。自定义资源包 v1 与手机基础能力并行设计，在标准订阅闭环稳定后接入。支持文件导入作为首版后续项，系统文件选择的流程单独验收。

iOS PiP、系统 AirPlay、复杂投屏、多画面、录制、跨设备云同步及高级后台能力放入后续阶段。用户需要的核心连续播放必须先在真机验证。后台刷新不承诺按固定周期准时执行。

## 5. 发布与审核准备

遵循仓库 `AGENTS.md`：现有七个平台正式发布仍需同版本、同基础构建号、同源提交、推送 main 后构建，并完成既有发布检查。本次规划不改变该政策。iOS 在开发与测试阶段独立标记；正式加入版本与产物矩阵前，先更新发布文档和校验工具的规划，明确 App Store 审核等待期间其他平台的发布协调方式。

提审需完整说明自定义资源包、同步和任何服务器专属协议能力，并提供可测试的授权示例。协议自定义和数据下载本身不保证审核通过，也不能解决未经授权的内容服务问题。现有应用服务的关系按真实情况说明。

P6 前逐项核实：开发者账号、Bundle ID、签名、图标、隐私政策、数据收集清单、隐私清单及所用 API 声明、媒体库许可证、最低系统版本、后台模式、ATS、局域网权限及其他实际使用权限。只有实际需要才申请权限。账号与真机条件目前未知，不要求用户在规划阶段操作。
